## Decisions (approved)

Decided by the autopilot planner (no owner available); each is logged in `docs/process/DECISIONS-PENDING.md` and can be vetoed.

1. **Start with Windows in M4.** The switch is live and saves `os.startWithWindows` (default off); registering the app with Windows (autostart plugin, 05) comes with M10's autostart work, which applies the saved value. Why: the roadmap puts autostart in M10 and doing it now would add a dependency to M4; nobody uses the app before the release.
2. **"Keep running in the tray when closed" (F-28.1)** is not shown in General until M10. Why: its behaviour (tray) is M10; a switch that does nothing misleads, and other sections also add their rows with their milestones.
3. **Shortcut groups (F-19.3; the mock is one flat grid).** Review: Next step `]`, Previous step `[`, Mark step reviewed `Space`, Next hunk `J`, Previous hunk `K`, Next note `N`, Add to drafts `D`, Dismiss note `X`, Comment on line `C`, Ask Claude `A`, Primary action (plan, re-review) `Enter`. Code: Go to definition `F12`, Find usages `Shift F12`, Open in Rider `Ctrl Shift O`. App: Open anything `Ctrl K`, Settings `Ctrl ,`, Switch Focus / Detailed `Ctrl D`, Sidebar layout `Ctrl 1`, Minimal layout `Ctrl 2`, Guide layout `Ctrl 3`, Close popover `Esc`, All shortcuts `?`. Each group has a small uppercase heading over its own grid in the mock's row style. Why: F-19.3 asks for the groups; the labels and keys stay the mock's.
4. **The mode toggle is per session.** Focus/Detailed and `Ctrl+D` change the session's mode only; Settings › General › Start in is the mode of new sessions and is not rewritten by the toggle; Start step 1 and Continue open the session's mode. Why: Start in is an explicit preference that a quick look at Detailed shouldn't change (least surprise); per session matches F-07.9.
5. **Split/Unified and Ignore whitespace (S-04 file bar).** One value for the whole Detailed view (shown on every file bar), kept for the app run, default Split with whitespace shown; Focus stays split (F-07.4). Ignore whitespace is display only: a removed and an added line that are equal once whitespace is removed show as one unchanged line; hunks stay in their step, notes, line numbers and coverage don't change. Why: it behaves like `git diff -w` without changing the hunk IDs that the coverage invariant and note anchors rely on, and one value means fewer clicks.
6. **"Show inline" (a Tweak of the mock).** No control; Detailed always shows the full callouts inline and lists the notes in the aside. Why: F-19.1 lists the General settings exactly, and the Tweak is a mock device.
7. **Answers in Detailed.** The answer card (M3 decision 4) shows in the guide aside right above the Ask box; **Ask Claude** on a callout and `A` focus the Ask box with that context; the context reads "step 4 · L46–L57" with selected lines and "step 4" without. Why: consistent with layout C, which also has its ask input in a side panel.
8. **Analysis context places.** "step N" = the current step when its hunks touch the file, otherwise the first step in the current order that touches it; "skim" = only skim hunks touch it; "outside MR" = not in the diff (self-review: "outside the change", intro "Files Claude read in the repository:"). Why: the mock only shows other steps; naming the current step tells the reader the file is in front of them, and a self-review has no MR or worktree (M3 decision 15).
9. **Footer Claude status.** "Claude: " and the parts that apply, joined with ", ": "steps 5–6 ready" (the steps after the current one, in the current order, whose analysis is ready; ranges; "step 5 ready" for one), "analyzing 7" (the step task running now), "step 7 failed"; with none of them "Claude: idle". When Claude Code is unusable the square turns orange and the text is the S-01 chip's ("Claude Code: not signed in", "Claude usage limit reached"…). Why: the mock's line is about the steps ahead (prefetch); the current step's state is already in the notes area.
10. **Footer code version.** MR sessions "worktree @ a3f9c12" (the review worktree's head); self-review of commits or a branch "repository @ <short head>"; local changes "working tree". Why: it says which code Claude reads, and a self-review has no worktree.
11. **The last step.** The S-04 end card on the last step reads "End of step 8", "That was the last step." and **Finish review** (yellow, in place of Next step), opening S-05; `]`, S-03's next arrow and B's toolbar next do the same on the last step (they were disabled in M3). Other steps: "Next: <title> · N files · +add −del" (the rail's numbers). Why: 02 S-05 lists "last step's Next" as an entry, and the mock shows only a middle step.
12. **Self-review in Detailed.** Info header "To fix N" in place of "Drafts N" and no pipeline; rail counts are kept notes; callouts **Keep to fix** (D) and **Edit and keep**; the composer's button **Keep to fix** with "Kept to fix. It's on your list at the end."; no thread items. Why: the same copy as S-03 in self-review (M3 decision 2, F-17.2).
13. **Line composer (F-09.7).** Neutral tag "COMMENT" with "L46" (old-side lines "old L46"), placeholder "Write a comment…"; with several lines selected it opens under the last one and the draft is anchored there (`DiffPosition` is one line); `C` without a selection uses the first changed line of the current hunk (J/K), else the step's first changed line. After **Add to drafts** the card keeps the text with "Added to drafts. It reaches GitLab only when you publish." and **Undo** (deletes the draft); manual drafts show this way under their lines when the step is reopened. Cancel/Esc discards. Why: the F-09.3 confirmation pattern, and the user sees their own comment where they wrote it.
14. **Review keys.** J/K move a current hunk over all files of the step in diff order, scroll it to the top and show the focus outline on its hunk header, stopping at the ends; N wraps ("cycles"); D/X act on the focused note (N's, else the first in line order) and do nothing on a decided note; `Ctrl+Shift+O` opens the current file at the current line (selection, focused note or current hunk) on S-03/S-04 and the shown file on S-06. Single-letter keys don't fire in text fields or with Ctrl/Alt held (AltGr on Polish keyboards) but do fire while a button has focus; Space and Enter leave a focused button to itself. Why: visible focus (WCAG 2.4.7), predictable ends, and a keyboard-only review where focus often rests on a button.
