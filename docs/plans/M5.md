## Decisions (approved)

Decided by the autopilot planner (no owner available); each is logged in `docs/process/DECISIONS-PENDING.md` and can be vetoed.

1. **Reply sends now.** **Reply** on a thread card opens a composer under the thread in the note-card style (placeholder "Write a reply…", **Reply** yellow, **Cancel**; `Ctrl+Enter` sends, `Esc` cancels); the reply posts to GitLab at once (`gitlab_reply`) and appears in the thread; it is not a draft. Why: ADR-004 and 06 T7 list reply as its own explicit action and 04 already has `gitlab_reply`; a draft reply would look sent while it isn't.
2. **Thread action feedback.** Resolve, Reopen and Reply show a busy state on their button; on failure the card keeps its state and the reply text and shows one line under the buttons: "Couldn't resolve the thread. <reason>", "Couldn't reopen the thread. <reason>", "Couldn't send the reply. <reason>". Why: the error shows where the user acted, and nothing typed is lost (Nielsen: visibility, error recovery).
3. **Threads in Detailed mode.** S-04 shows the same thread cards and actions under their lines as S-03; the aside doesn't list them. Why: F-11.1 doesn't depend on the mode and 02 says S-04's states are S-03's.
4. **Where a thread shows (F-11.3).** "Same line text" ignores leading and trailing whitespace; the nearest match to the interdiff-mapped line within ±20 wins, ties go to the upper line. The card shows on that line when it is inside a hunk of the step, with a neutral "OUTDATED" word tag when the thread was written on another version. With no match, or a match outside the shown hunks, the card shows on the file header in the first step (current order) that shows the file; a file no longer in the MR → S-05 only. A current thread on a line outside the shown hunks (an expanded-context comment in GitLab) also goes to the file header. Why: one place per thread avoids duplicate cards, and no diff thread disappears from the review.
5. **Opening tab of S-05.** Drafts when the session has unpublished drafts, else Threads; the choice is kept while the screen is open. Why: publishing is the frequent path after a review (fewest clicks); with nothing to publish the threads are the useful view.
6. **Drafts list rows.** Drafts without a severity (manual comments, answers) have no square; drafts without a position say "general comment" in place of `file:line`; the pencil turns the text into a text area with **Save** and **Cancel** (`Ctrl+Enter`, `Esc`), saved locally only; published rows stay with "· published", their checkbox ticked and locked, no pencil. Why: the square encodes severity (a gray one would claim "nit"); inline editing is the fewest clicks; published rows show what went out (mock).
7. **Publish button and banner.** "Publish (N)" counts the ticked unpublished drafts (the summary is not counted, as in the mock) and is disabled with nothing selected; with only the summary ticked and filled it reads "Publish summary". Success banner as in the mock: "Published N comments and a summary. The author got a single notification." ("comment" for 1; "Published a summary. …" without drafts). Drafts left unticked stay selectable for a later publish. Why: the mock's copy and arithmetic, and no "Publish (0)" that does something.
8. **Drafts already in GitLab's own review.** `bulk_publish` sends every pending draft note of the user on the MR, including ones written in GitLab's web UI. When such drafts exist (checked when S-05 opens and right before publishing), a yellow banner says "You have N draft comments in GitLab's own review. Publishing here sends them too." Publish stays available. Why: error prevention, nothing should reach GitLab that the user didn't knowingly send; publishing drafts one by one would send several notifications (against F-12.5) and deleting them would destroy the user's work.
9. **Partial failure.** Banner "Published 3 of 5. 2 failed: <reason of the first failure>." with **Retry**; each failed row keeps its checkbox and shows its own reason under `file:line` ("the line is no longer in the MR", "GitLab refused the token", "GitLab is unreachable", else GitLab's message); Retry sends only the failed rows still ticked and reuses GitLab draft notes already created, so nothing is published twice. Why: the S-05 state in 02, with the user seeing which comment failed and why.
10. **The MR changed since the review.** (a) Yellow banner "The MR has a new version since your review." with **See what changed** → S-09, a stub until M8; Approve is disabled while the MR's head differs from the reviewed head, which moves only when the new version is reviewed (S-09, M8). (b) Publish stays available and re-maps draft positions to the new version (05); a draft whose line no longer exists gets the "OUTDATED" tag, is unticked, and its location reads "`file:line` · line changed, published as a general comment"; if the user ticks it, it goes out without a position with `file:line` quoted. Why: approve must send the reviewed SHA and GitLab answers 409 to a stale one (S5); unticked by default is the least surprising way to "ask the user first" (05); stubs bridged later screens in earlier milestones (M3 decision 9) and nobody uses the app before the release.
11. **Summary comment (F-12.4).** Ticking "Add a summary comment" runs the summary task once (the tick is the explicit action; nothing runs in the background); while it runs the label reads "Claude is writing a summary…" and the text area stays editable; anything the user types wins and the suggestion is dropped; on success the label is "Suggested by Claude, edit as you like" (mock); on failure "Couldn't suggest a summary." with **Retry** and an empty area; with Claude unusable the area is empty without a label. The tick and the text are kept per session; an empty summary isn't published. Why: the spec prefills on the tick, a suggestion must never overwrite the user's words, and the owner wants Claude to run only on an explicit action.
12. **Thread check on click (F-13.3).** A **Check with Claude** button (purple Claude square) on the Threads tab, shown when at least one open thread was written on an older version; chips "Claude: <hint>" on the open threads Claude judges addressed; "Claude found no thread addressed by a later commit." when none; "Couldn't check the threads." with **Retry**; results cached per head and thread set; nothing is resolved by Claude. Why: the spec doesn't say when the check runs, and the owner wants every Claude run started by an explicit button (no automatic runs).
13. **Threads list.** Lists resolvable threads only (diff and general); non-resolvable single comments are not shown; the user's own threads say "You" (mock); general threads have no `file:line`; **Show in code** opens the step the thread shows in (decision 4) in the session's mode with the card scrolled into view, hidden for threads in no step. Why: F-13.1's Open/Resolved split only exists for resolvable threads, and the mock's link needs a target.
14. **Approval tile edge cases.** "Approvals: X of Y"; "Approvals: X" when the MR requires none; Approve disabled with "GitLab doesn't let you approve this MR." when `user_can_approve` is false, and with "This project asks for your password to approve. Approve it in GitLab." when `require_password_to_approve` is true (the app never handles passwords); errors show under the button; no confirmation dialog (Revoke undoes it); "All threads resolved." also when there are no threads. Why: honest numbers, the spec's copy kept, and no password handling (06).
15. **Drafts-only sessions (F-12.7).** S-05 without the progress line and without **Back to steps** (there are no steps); such a session appears in "Pick up where you left off" while it holds unpublished drafts (the card shows the draft count only, **Continue** → S-05); opening a new review of the same MR moves its unpublished drafts into the new session. Why: drafts belong to the MR and must never be stranded.
