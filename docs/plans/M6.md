# M6 plan · Pipelines

Written by the autopilot planner on 2026-10-19. Branch `m6-pipelines`, cut after M5 (7ca93aa). The owner may veto any decision below; vetoes come back as rework items. Each item applies the doc change of its decisions (02 S-08, 05 GitLab › Pipelines and Tasks, 04 IPC) before the code. Goal (07): see and run the MR's pipeline and jobs from the app and understand failures; demo on the stand-in with a runner on the PC: run a new MR pipeline, play a manual job with a variable, retry a failed job, Explain failure → Add to drafts.

S-08 is MR-scoped, not session-scoped (route `/mr/:iid/pipeline`): every command takes the GitLab `project` of the active repository and the `iid` (like `drafts_create_for_mr`), the core never trusts a project or URL from the UI beyond that pair. All GitLab calls go through the existing `gitlab/client.rs`; all writes are separate explicit clicks (06 T7, T9).

## Decisions (approved)

Decided by the autopilot planner (no owner available); each is logged in `docs/process/DECISIONS-PENDING.md` and can be vetoed.

1. **Status words beyond the four in F-20.1.** The status block uses the app's existing `PipelineState` words: Passed, Failed, Running (also `created`, `pending`, `preparing`), Waiting (`waiting_for_resource`, `scheduled`), Canceled, Skipped, Manual (a pipeline blocked on a manual job). Why: GitLab has more pipeline states than the four in the spec, and the same words already show in S-01, S-02 and S-04 (consistency, match the user's language).
2. **Allowed-failure tag.** Shown only on a passed pipeline: "1 allowed failure", "2 allowed failures". Why: the mock shows it only next to Passed, where it explains why a red job didn't fail the pipeline, and plural copy is correct English for N > 1.
3. **Tabs and meta line.** All the MR's pipelines are tabs, newest first; the strip scrolls sideways and keeps the selected tab in view; a tab reads `#number` over "version N" (+ " · latest" on the newest pipeline), without a version when the SHA matches no MR version. The meta line is "#number · <kind> · <sha> · version N · <author> · <age> · <duration>", with "started by you" for the user's own pipelines; kind is "Merge request pipeline" (`merge_request_event`), "Branch pipeline" (`push`), else GitLab's source in words; a canceled pipeline says only what GitLab reports (no "canceled by a newer push", which REST doesn't tell). The page opens on the newest pipeline. Why: the mock's labels, honest data only, and the latest pipeline is what the user usually wants (fewest clicks).
4. **Back link.** "Back to review" when S-08 was opened from a review screen (S-02 to S-05), returning to that screen; "Back to MRs" when opened from S-01; both go back in history. Why: the mock's label fits only the review path, and the link should name where it goes (recognition over recall).
5. **Stage order.** Stage columns follow the order GitLab created the jobs in (job id ascending, first appearance of each stage); a column header shows the stage name. Why: the REST Jobs API has no stage index, and GitLab creates jobs stage by stage (verified first; GraphQL fallback).
6. **The one row button.** failed and canceled → **Retry**; running, pending and waiting → **Cancel**; manual → **Run** (selects only); passed and skipped → no button (Retry stays in the job details). Retry and Cancel act at once without confirmation, as do **Retry failed jobs** and **Cancel pipeline**. Why: F-20.2 names three buttons and says they act at once; a Retry on every passed row would add noise and an easy misclick; pipeline-level retry and cancel are as reversible as the row ones.
7. **Live updates.** While S-08 is open and the selected pipeline has an active job, the pipeline and its jobs are re-read every 5 s; the log of a running job every 3 s; nothing is polled for finished pipelines or when the screen closes; a manual job that reads `created` is polled until it is `manual`. Why: "shows the new pipeline live" and "streaming while running" without hammering GitLab (05 keeps the poller to a small burst).
8. **Action failures.** Each action shows a busy state on its button; a failure shows one line under the actions row: "Couldn't run a pipeline. <reason>", "Couldn't retry the job. <reason>", "Couldn't cancel the job. <reason>", "Couldn't play the job. <reason>", "Couldn't retry the failed jobs. <reason>", "Couldn't cancel the pipeline. <reason>", where the reason is GitLab's message in plain words (e.g. "No stages / jobs for this pipeline."). Why: the same pattern as M5 decision 2 (error where the user acted, nothing lost).
9. **Insufficient permission.** After any pipeline or job write returns 403, every write action on S-08 (row buttons, pipeline actions, Run new pipeline, Run `<job>`) is disabled for this MR until the screen reopens, with GitLab's 403 message as the tooltip and as an accessible description; nothing is pre-checked. Why: S-08's state in 02 says "tooltip from GitLab's 403 message", and GitLab decides permissions per branch, so only its answer is reliable.
10. **Log lines.** The log panel shows the last 500 lines with ANSI colors and GitLab section markers removed (text only, never HTML); a line is a command when it starts with `$ `, an error when GitLab colored it red or it starts with `ERROR`, `error`, `Failed`, `FAIL` or contains ` error ` / `Error:`, a pass when GitLab colored it green or it starts with `✔`, `Passed`, `PASS`, `Job succeeded`, else plain; when lines were cut, a first line reads "Showing the last 500 lines. Full log opens it in GitLab." Why: S-08's "log too long" state, the mock's three colors, and ANSI color is the job's own signal where it exists.
11. **Manual job variables.** Names must be letters, digits and `_` (GitLab's rule); a row with an invalid or empty name and a value blocks **Run `<job>`** and its name field says "Letters, digits and _ only."; empty rows are dropped; values are sent and stored as typed (they may be secrets the user chose to pass; stored like other job settings in SQLite, never logged). The last values are saved only when the play succeeds. Why: error prevention before GitLab refuses the call, and F-20.6's "last values used" means values that actually ran.
12. **What Explain failure reads.** It runs in the MR's review worktree; when there is none or it isn't at the MR's latest head, the app prepares it first with the existing preparation (fetch + worktree, no plan) and the panel says "Preparing the code…" before "Reading the log and the diff…". The diff file holds the MR diff at the latest head and, for a pipeline on an older version, the changes from the pipeline's SHA to the head. Why: Claude needs the code to cite evidence (05 requires evidence in the worktree), and "Already fixed in version N" needs what changed since the failing run.
13. **Opening GitLab in the browser.** **Open in GitLab**, **Full log** and artifact **Download** open the GitLab page in the default browser; the core only opens `https` URLs on the configured GitLab host. Downloads use the browser's own GitLab sign-in (the token never leaves the core). Why: consistent with S-08's "Full log opens it in the browser", the browser shows download progress and handles auth, and a host check prevents opening anything else (06 T5).
14. **Explain failure states.** Button with the purple square on failed jobs (allowed failures too), disabled with the tooltip "Claude isn't available" when Claude can't run; verdict tag colors: Caused by this MR orange, Already fixed in version N green, Flaky and Unrelated blue, Unknown gray; with `retry_recommended` a line "A retry may help." under the explanation; evidence chips: `file:line` opens that file in the MR's latest review session (its step and mode) when one exists, else plain text; `pipeline #N` selects that tab; **Add to drafts** adds the suggested comment unchanged as a general comment (editable in S-05) and turns into the confirmation; no suggested comment → no block; a result stays cached for that job. Why: the mock's copy and colors, the owner's rule that Claude runs only on a click, and the edit already lives in S-05's drafts list.
15. **"Retried: failed again on the same test."** Shown on a failed attempt whose previous attempt of the same job in the same pipeline failed on exactly the same set of tests; nothing is shown when the tests differ or no test names are known. Why: the spec's copy speaks of a test, and a wrong "same test" claim would mislead more than silence.
16. **Pipeline link in S-01 rows.** The pipeline status in an MR row becomes its own link (own tab stop, same look) next to the row's open button; clicking it opens S-08 and doesn't prepare a review. Why: a link can't sit inside the row's button (invalid HTML, unreachable by keyboard), and F-20.10 asks for a link everywhere.
