# M7 plan · Own code: fix, author mode, new MR

Written by the autopilot planner on 2026-10-20. Branch `m7-own-code`, cut after M6 (5759c37). The owner may veto any decision below; vetoes come back as rework items. Each item applies the doc change of its decisions (01 F-25/F-26/F-27, 02 S-05/S-10/S-11, 04 IPC, 05 git and GitLab rows) before the code. Goal (07): the author's side: answer feedback, fix with Claude or Rider, commit as fixup, push and reply; create MRs. Demo on the stand-in: on your MR, Fix with Claude → Accept → Commit (fixup) → Push and reply → thread resolved; create a new MR from a local branch.

Ground rules for every item: Claude edits only own code (local or commits self-review of the current checkout, or an MR whose author is me), one file, in an ADR-018 scratch worktree, argv only from `runner.rs` `fix_args` (exists, S4); the user's checkout is written only on Accept and only through a pathspec commit and a plain push (no stash, reset, checkout, rebase, force-push); every GitLab write (reply, resolve, create MR) follows an explicit click; no new automatic Claude run (owner direction 2026-10-14): every Claude task in M7 starts from its own button.

## Risks

- `git commit --fixup=<sha> -F -` with a body and a pathspec: pinned by a fixture test on the PC's git before the UI uses it; if git rejects the combination, the message goes in as `-F` with the `fixup! <subject>` line written by the core.
- Fix profile on Claude Enterprise (`Edit(/…)` under `--restricted`) is proven only on PC/Max (S4); field visit 4a checks it on the laptop. `gr-probe` gets key-set rows for `members/all`, the merged-MR history query (decision 17) and create MR (status codes only).
- GraphQL `diffStats { path }` on merged MRs: verified on the stand-in (17.11.7) by introspection first; missing → REST `GET …/merge_requests/:iid/diffs` per MR, capped at 50 MRs.

## Decisions (approved)

Decided by the autopilot planner (no owner available); each is logged in `docs/process/DECISIONS-PENDING.md` and can be vetoed.

1. **Where Fix with Claude appears in self-review.** On each "to fix" item of the self-review summary (F-17.4 already promises it) and in the self-review note card's More menu; the fix card opens under the item or card. Why: F-25.1 says "self-review notes" and the summary is where the fix list lives; the More menu keeps Keep to fix as the card's primary action (consistency with M3 decision 2).
2. **After Accept in self-review.** The item shows "Applied to your working copy." with **Browse and commit** (→ S-06); no commit panel in S-05. Why: S-06 is the existing commit place for local changes; one commit flow avoids two places that commit.
3. **Claude made no edit** (`changed: false`). The card says "Claude made no change." with Claude's sentence and **Close**; nothing to accept. Why: the schema allows it and the user must see why there is no diff (visible state).
4. **One fix at a time.** While a fix runs or a proposal waits, other Fix buttons are disabled with the tooltip "Finish the open fix first." Why: two proposals on the same checkout make the stale-file check fail for one of them (error prevention).
5. **Thread tags in S-10.** Question = unresolved thread whose first note ends a sentence with "?"; Change requested = any other unresolved thread (GitLab suggestions included); Fix proposed = an open proposal; Fixed locally · not pushed = a queued reply exists; Replied = my reply sent on a change thread, still open; Answered = question whose last note is mine; Resolved = resolved (folded into "N resolved earlier"). "N THREADS TO ANSWER" counts unresolved threads whose last note isn't mine. Why: the spec names the tags but no rule; a deterministic rule needs no Claude run (owner direction) and mistakes are harmless because every action is still available through Reply.
6. **Diff shown in S-10.** The thread's file as `merge-base(origin/<target>, HEAD)` → working tree, unified, scrolled to the thread line, so local fixes show at once; a General thread shows only its conversation. Why: 02 S-10 says "git.diff(worktree=own checkout)" and the mock is unified.
7. **Fix in Rider watch.** Waits for a content change of that one file, with **Stop waiting**; changes elsewhere are ignored. Why: the thread points at one file, and an exit keeps the user in control (user control and freedom).
8. **Fixup target.** The commit that last changed the thread's line (`git blame -L`) when it lies in merge-base..HEAD; else the newest commit in that range touching the file; else HEAD. Why: autosquash folds the fix into the commit the reviewer commented on, which is what "fixup" implies.
9. **Suggested commit message without Claude.** Prefilled with Claude's explanation after Fix with Claude, or "Address review on <file>:<line>" after a Rider change; **Suggest** (existing commit-message task) is there on click. Why: the owner allows Claude only on explicit clicks, and the fix explanation already exists.
10. **Other uncommitted changes.** Warning only ("You have other uncommitted changes. They won't be part of this commit."), no Stash link; the commit uses a pathspec so only the fixed file goes in. Why: stashing would change the user's working copy, which the non-negotiables keep the app away from, and the pathspec already makes the warning true.
11. **Behind remote check.** Before Push and reply the app runs `git ls-remote origin refs/heads/<branch>`; a remote sha that isn't an ancestor of HEAD shows "Pull first" ("The remote has commits you don't have. Pull with rebase in Rider." with Rider open), nothing pushed. Why: read-only, changes no local ref, and matches S-06's push-rejected copy.
12. **Queued replies after a restart.** A queued reply whose commit is on the remote shows "Pushed. Reply not sent yet." with **Send reply**; never sent by itself. Why: nothing reaches GitLab without an explicit click.
13. **New pipeline link.** Polls the MR pipelines for the pushed sha up to 30 s; until found the link reads "Pipeline starting…" and opens S-08. Why: GitLab creates the pipeline asynchronously, and the link must not point at the old pipeline.
14. **Read-only author mode keeps replies.** Reply, Draft with Claude and Send reply stay when the checkout is on another branch; only Fix, Commit and Push are hidden. Why: F-26.8 hides exactly those three, and answering a question needs no checkout.
15. **MR description without an automatic Claude run.** S-11 opens with a title from the commits and an empty What / Why / How to test skeleton; **Write with Claude** in the regenerate slot fills it, then the slot offers Shorter / Longer version. Opening S-11 from the self-review's **Draft MR description** starts the task, because that click asks for it. Why: the owner's rule "every Claude call only after a click" outranks the word "prefilled" in F-27.2; the doc change goes into F-27.2 and S-11.
16. **Regenerating over edits.** If the user edited the title or description, Shorter / Longer / Write ask "Replace your edits?" first. Why: never overwrite typed text silently (same rule as Amend in S-06).
17. **"Reviewed N MRs in <area> this month."** Area = the directory name holding most changed lines (e.g. `Views`); "this month" = the last 30 days; counted from merged MRs of the project where the person was a reviewer and a changed path is under that directory (GraphQL `mergeRequests(state: merged, mergedAfter:)` with `reviewers` and `diffStats{path}`, first 100). Why: the spec gives the copy but no source; this is the cheapest source with the right meaning.
18. **Suggestions list.** At most 3 people, me and bots excluded, ranked code owner > blame share > history, each with its strongest reason; blame authors are matched to project members by name, then by email local part = username; unmatched are dropped. Why: the mock shows three with one reason each, and a wrong match is worse than none.
19. **Which checks block Create.** Not pushed and an existing MR disable Create (GitLab needs the remote branch; a second MR is an error); conflicts and a missing self-review are orange warnings only ("Self-review not done" · "No self-review of this branch yet."). Why: GitLab accepts MRs with conflicts and self-review is optional; blocking would add clicks for a reversible situation.
20. **Target list.** `origin/*` remote-tracking branches, default = the GitLab project's default branch; the conflict check uses `origin/<target>`. Why: the MR merges into the remote branch, not a possibly stale local one.
